# 루트 API 조회 경로 개선

> 아래 속도·크기·응답 동일성은 인덱스 적용 당시의 기록이다.
> 후속 [요약 정리](root_summary_contract.md)에서 요약 필드와 설명 중복 목록을 변경했다.
> 인덱스와 달력 데이터 보존 정책은 그대로 유지하며, 현재 크기는 측정 명령으로 확인한다.

2026-11-13. 사용자는 프론트엔드 연동을 보류하고 루트 API 개선에 집중하도록 요청했다.
첫 단계로 실제 응답의 처리 시간·크기를 측정하고 확인된 달력 조회 병목을 해결했다.

## 문제와 적용

저장소의 기존 `manseryuk.db`는 달력 73,442행에 날짜 조회용 인덱스가 없었다.
`EXPLAIN QUERY PLAN`에서 양력·음력 날짜 조회가 `SCAN calenda_data`로 확인됐다.
모델의 기존 단일 열 인덱스 선언은 실제 DB에 적용되지 않은 상태였다.
단, 절기 번호 `cd_no`는 실제 테이블에서 정수 기본키이므로 기존 rowid 조회를 사용한다.
프로파일링에서도 달력 날짜·절기 조회가 처리 시간의 큰 비중을 차지했다.

다음 비고유 인덱스를 실제 DB에 적용했다.

| 인덱스 | 열 | 대상 |
| --- | --- | --- |
| `ix_calenda_data_solar_date` | `cd_sy, cd_sm, cd_sd` | 양력 날짜 |
| `ix_calenda_data_lunar_date` | `cd_ly, cd_lm, cd_ld, cd_leap_month` | 음력 평달·윤달 날짜 |

양력·음력 복합 인덱스 2개는 모델에도 선언했다.
절기 번호 범위는 기존 `INTEGER PRIMARY KEY` 경로를 사용하는 것을 확인했고 중복 인덱스는 추가하지 않았다.
비고유 인덱스이므로 기존 중복 자료를 지우거나 중복 날짜의 오류 판정을 우회하지 않는다.
새 API·응답 필드·관계 판정·계수 변경·전역 응답 캐시는 추가하지 않았다.

## 기존 DB 적용과 측정

이 저장소에 포함된 DB에는 이미 적용했다. 별도로 보관 중인 기존 DB에는 다음을 실행한다.
SQLAlchemy의 `create_all()`만으로 기존 테이블의 새 인덱스가 적용된다고 가정하지 않는다.

```bash
.venv312/bin/python scripts/add_calendar_lookup_indexes.py --database /path/to/manseryuk.db
```

기존 파일·테이블만 사용하며 날짜 행을 생성하거나 변경하지 않는다.
재실행하면 기존 인덱스를 보고하고 추가 생성하지 않는다. 같은 이름인데 열·고유성·조건이
다른 인덱스가 있으면 다른 인덱스를 생성하기 전에 오류를 반환한다.
신규 테이블은 모델 메타데이터의 인덱스 정의를 따른다.

루트 API의 현재 크기와 시간을 다시 확인할 때:

```bash
.venv312/bin/python scripts/measure_root_api.py --repeat 8
```

다른 DB를 사용하려면 `--database /path/to/manseryuk.db`를 지정한다.
이 측정은 DB를 읽기 전용으로 열고 실제 FastAPI 응답 검증·직렬화를 포함한다.
고정 입력마다 1회 준비 요청 후 지정 횟수만큼 요청하고 중앙값과 응답·섹션별 바이트 수를 출력한다.
실제 프론트엔드, 네트워크 지연, 운영 동시 요청·부하 테스트는 포함하지 않는다.

## 측정 결과

동일 프로세스에서 원본의 읽기 전용 복사본과 인덱스 적용 DB를 교대로 요청했다.
고정 입력별 준비 요청 후 각 DB에 30회 요청한 중앙값이다. 수치는 해당 실행의 관찰값이며
운영 환경의 속도나 지연 상한을 보장하지 않는다.

| 입력 | 적용 전 | 적용 후 | JSON 크기 |
| --- | ---: | ---: | ---: |
| 양력 1995-05-12 14:30 남 | 24.19ms | 15.63ms | 105,116 bytes |
| 양력 1990-01-08 18:00 남 | 21.28ms | 12.96ms | 97,621 bytes |
| 음력 윤달 2023-02-01 00:00 여 | 21.44ms | 13.44ms | 89,241 bytes |
| 양력 2000-02-29 23:59 남 | 19.89ms | 12.90ms | 88,092 bytes |

요청·측정값·데이터 해시는 [측정 JSON](root_api_lookup_measurements.json)에 보존했다.
위 네 입력의 반복 요청에서 상태와 JSON 전체 내용은 적용 전후 동일하다.
응답 크기는 줄이지 않았다. 첫 사례에서 `cycles`는 약 33.5KB,
`advanced_analysis`는 약 50.8KB이며 `ten_gods`·신살 이름 맵의 크기는 상대적으로 작다.
응답 크기만을 근거로 자료를 삭제하거나 필드 선택용 새 API를 만들지 않았다.

인덱스 때문에 DB 파일 크기는 8,216,576에서 10,596,352 bytes로 늘었다.
달력 73,442행은 동일하며 `rowid` 순서로 직렬화한 전체 행의 SHA-256은 적용 전후 같다.

```text
f3291ed7a4c659d5c2d816e4ff3b351575cdbbc9f456cb06cc564cd202050cde
```
